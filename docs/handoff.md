## 経緯（なぜこの方向に進んでいるか）

1. Home Assistantで「いつ何をしていたか」の活動ログ（就寝中/作業中/休憩中/外出中、将来的にはもっと細かく）を可視化したい、というのが元々のゴール
2. 既存のモーションセンサーは玄関付近にしかなく、リビングでの在宅勤務中の在室・静止状態を検知できない、という制約が判明
3. mmWaveレーダー（Aqara FP2やSeeed XIAOシリーズ）を検討したが、技適（技術基準適合証明）の確認・取得の手間が課題として浮上
4. 代替として、既に技適済みのWiFi無線をそのまま使う「WiFi CSI（Channel State Information）センシング」を検証する方針にした。専用レーダーHWの購入・技適確認が不要なのが利点
5. 実装方式はESPHome + `espectre`外部コンポーネントも検討したが、コードレベルの細かい制御がしたいという要望から、**PlatformIO + Arduino framework**での自作ファームウェアを本命ルートとして選択
6. **重要な制約**：この検証段階ではMQTT/Home Assistant連携は行わない。まずは生の数値を見て、そもそもCSIが人の動き・在室状態に反応するかどうかだけを確認する

## 用語について（CSI取得方式の3分類）

Espressif公式`esp-csi`のREADME（4.1〜4.3）で使われている分類・名称に統一している。

- **RouterCSI**（ルーターCSI方式、公式4.1「Get router CSI」）：ESP32がルーターにパケットを送り、その応答に乗ったCSIを取得する。現状の`main.cpp`の実装がこれ。ESP32単体＋ルーターだけで完結する最もシンプルな方式
- **InterDeviceCSI**（デバイス間CSI方式、公式4.2「Get CSI between devices」）：複数のESP32が全てルーターに接続しつつ、互いの送信パケットに乗ったCSIを傍受し合う方式。ルーターの設置位置に依存しにくい。**このプロジェクトではまだ未検討・未実装**
- **SpecificDeviceCSI**（専用デバイスCSI方式、公式4.3「Get CSI specific devices」）：専用の送信機1台がチャネルを切り替えながらパケットを送り続け、複数の受信機がそのCSIを取得する。ルーターに依存せず精度・信頼性が最も高いとされる。TX/RXペア構成や、将来構想のTX1台+RX複数台のブロードキャスト型構成はこれに該当

## ファームウェアの現状（`src/main.cpp`）

PlatformIO + Arduino framework、`esp_wifi_set_csi_rx_cb`でCSIコールバックを受ける。シリアル出力とWiFi UDP送信（サブキャリア別振幅）の両方に対応している。

- `rssi`：受信パケットの信号強度。近い/遠いの粗い判定に一番安定して使える
- `avg_amp`：CSIバッファの生バイトを空間方向に絶対値平均したもの。動きへの感度は低め
- `diff_score`：前フレームとの差分の絶対値平均。**既知の問題（未修正）**：192本全帯域を平均しているため実質ノイズに埋もれている。サブキャリア0〜50帯（Legacy LTF、AP側のレート制御に依存しないクリーンな帯域）だけに絞れば動きに鋭く反応することが判明済み（`#17`）。ファームウェア側の修正はまだ行っていない（次のアクション候補1）
- `filt=採用数/受信総数`：CSIコールバックの送信元MACが接続中APのBSSIDと一致するものだけを採用するフィルタの採用率。実測では常に100%（フィルタは実質何も除外していない、`#7`）
- サブキャリアごとの振幅（`sqrt(I²+Q²)`）をWiFi UDPでPC(`tools/csi_listener`)へ送信する機能あり。送信先IP・ポートは`src/secrets.h`の`PC_IP_ADDR`で設定する

**WiFi認証情報・送信先IPは`src/secrets.h`（`.gitignore`済み）に分離済み**。テンプレートは`src/secrets.h.example`。新しい環境でビルドする際はコピーして値を入れること。

## ツール構成（`tools/`）

- **`tools/csi_listener/`**：PC側でCSIデータ・位置報告を受信するリスナー。Docker化済み（`docker build -t csi-listener .` → `docker run -p 5005:5005/udp -p 5006:5006/udp -v ./data:/data csi-listener`）。UDP:5005でサブキャリア振幅データ、UDP:5006でスマホからの位置報告（JSON）を受け、それぞれCSVに書き出す。**Windows Git BashでDocker実行する際は`MSYS_NO_PATHCONV=1`を付けないと`-e`の値のパスが勝手にWindowsパスへ変換されて壊れるので注意**
- **`tools/position_reporter/`**：Flutterで作ったAndroidアプリ。「椅子」「ベッド」「玄関」「不在」ボタンをタップすると、その場でPC(`tools/csi_listener`)へUDP(JSON)で位置ラベル+時刻を送る。ビルド・実機インストールは`flutter build apk --release` → `adb install -r build/app/outputs/flutter-apk/app-release.apk`（`flutter run`は使わないこと）。`AndroidManifest.xml`に`INTERNET`権限が必要

## 確立した知見（要点のみ、詳細は research_log.md）

- 粗い在室/不在（近づく・離れる）は`rssi`の平均値シフトだけで検出できる（`#1`,`#2`）
- **チップの種類（S3 vs C3）はCSIセンシング性能に影響しない。信号品質を左右するのはアンテナ実装（自作PCBトレース vs 外付け）**（`#8`〜`#10`）
- 近接場（ノードのすぐ近くを人体が塞ぐ）と経路遮蔽（ノード↔ルーター直線上を人体が塞ぐ）は物理的に別の現象で、rssiの反応パターンが質的に異なる（`#11`,`#12`）
- **経路遮蔽仮説**：ノード↔ルーター間の直接伝搬経路（フレネルゾーン）を人体が遮ったかどうかが、ゾーン分離の支配的要因。フレネルゾーン半径`F1=√(λ・d1・d2/(d1+d2))`に基づき「監視したいゾーンが経路の中間点に来る」よう配置すると分離度が劇的に改善する（実測でchair-away分離比0.9倍→5.22倍、`#13`,`#18`）
- ノードの設置意図で「ゾーン占有センサー」（経路上に留まる場所を置く）にも「通過検知センサー（トリップワイヤー）」（経路上に通過点を置く）にもなる。後者は滞在判定はできないが、通過の瞬間をほぼ100%検知できる（`#20`）
- 布団のような軽い物体は近接場では人体の代わりにならないが、経路遮蔽では材質を問わず質量があれば遮蔽効果が出る（`#15`）
- AP側の共通ドリフト（レート制御等、ESP32側では制御不能）に注意。単一ノードのrssi絶対値だけで判断せず、複数ノード間の差分を使うとドリフトが打ち消される——**ただし両ノードがそれぞれゾーン依存の変化を持つ場合に限る**。片方がトリップワイヤー化すると打ち消し効果が失われる（`#16`,`#17`,`#20b`）
- サブキャリア0〜50帯（Legacy LTF）の前フレーム差分（"乱れ"）は、AP状態に依存しないクリーンな動き検知指標。移動の瞬間に鋭く反応し、2ノード間の乱れピークの順序・大きさで移動方向を判別できる（`#17`,`#18`追加検証,`#20c`：10/10正解）
- 「椅子にいるかどうか」の2値判定はrssi差分の最近傍分類でかなり高精度（ゾーン占有配置で92.7%、トリップワイヤー配置で80〜85%）。**デバウンス（数秒連続で確定）は逆効果**——誤判定の多くはノイズでなく「センサーがアプリのタップより早く動きを検知しているラベル遅延」のため（`#19b`）
- rssi差分（静止位置）とサブキャリア乱れピーク（移動方向）を組み合わせた2段階分類器は、キャリブレーション設計のあるデータで51.8%→82%程度まで改善（`#19`,`#20d`）
- **2ノード間の乱れ順序による移動方向判定は、diff_score（サブキャリア乱れ）だけでなくrssiの移動平均でも成立する**：同一機種3台（ATOM Lite）でのトリップワイヤー2台のrssiに1秒移動平均をかけると、移動方向に応じて谷の発生順序が入れ替わり4/4で正しく判定できた（`#21`）。ただし谷の時間差そのもの（何秒前に通過したか）はタップ遅延の影響を受けやすくばらつきが大きい
- **C3単体のサブキャリア「形」（絶対レベルを引いた相対プロファイル）で、rssiドリフトによる誤判定を部分的に補正できる兆しがある**。rssi差分単体・形状単体・OR判定（どちらかが椅子なら椅子）を公正比較すると、総合精度はOR判定が最良（85.1%）だが、バランス重視（それ以外の見逃しを避けたい）なら形状単体が有力（それ以外recall97.7%）。少数サンプルでの結果であり再現性は未検証（`#20e`,`#20f`）

## 未解決・注意点

- 経路遮蔽仮説の直接検証（`#14`,`#18`）はいずれも1回きりの試行。複数回の再現性確認が引き続き課題
- `avg_amp`の標準偏差が初期の検証間で大きく異なる（2.63 vs 0.35）。原因未特定
- **AP側の共通ドリフトに注意**：複数ノードのrssi/CSIが、物理的な変化がなくても数分〜十数分のスパンで同時に同方向へシフトすることがある。単一ノードの絶対値だけで結論を出さず、複数ノードの相対関係（差分）や同時記録での比較を優先すること
- C3のサブキャリア形状によるドリフト補正（`#20e`,`#20f`）は全11区間という少数サンプルでの結果。再現性の確認が必要

## SpecificDeviceCSI実装のための調査メモ（2026-08-30時点、文献ベース）

Espressif公式`esp-csi`リポジトリ（[github.com/espressif/esp-csi](https://github.com/espressif/esp-csi)）を調査した結果。**この時点ではまだ実機検証していない、文献ベースの情報**（実機検証の結果は`#22`、下記「次のアクション候補」1番を参照。転送方式はユーザー判断でUSBシリアルのみ実装し、WiFi UDPとの比較検証は行わなかった）。

- **公式のTX/RX分離サンプルが存在**：`examples/get-started/`に送信専用`csi_send`・受信専用`csi_recv`があり、現状の`main.cpp`（自己送受信=RouterCSI）とは別に、これをベースにすればTX/RX分離の実装パターンがそのまま手に入る。より本格的な構成として`examples/esp-crab/`（`MASTER_RECV`/`SLAVE_RECV`/`SLAVE_SEND`）もあり、公式ドキュメントでは「専用送信機+専用受信機」構成は**広い空間範囲でのセンシング向き**、「自己送受信」は**近距離・高精度（ミリ単位）向き**と説明されている——今回のリビング全体の在室検知という用途は前者に近い
- **転送方式が現状と根本的に違う**：公式サンプルは「TX→RX間はESP-NOWプロトコルで無線トリガー」「RX→PC間はUSBシリアル」という構成（`csi_data_read_parse.py`がシリアルポートを読んで可視化）。現状のこのプロジェクトは「TX/RX同一ノードでWiFi STA接続」「WiFi UDPでPCの`tools/csi_listener`へ送信」なので、SpecificDeviceCSI化する際はRXノードからPCへの転送方式を再検討する必要がある
  - **ユーザー方針（2026-08-30決定→2026-09-03実施）**：当初はWiFi UDP継続案とUSBシリアル案の両方を実装して比較する予定だったが、実装時にUSBシリアル案のみを選択。`src/csi_rx.cpp`はUSBシリアルでCSVダンプする構成になっている
  - **設計上の前提（2026-08-31確認）**：どの構成（TX1台+RX1台のペア、将来のTX1台+RX複数台のブロードキャスト型いずれも）でも「純粋な受信のみ」のノードは存在しない。RXノードは必ず「CSI受信」＋「母艦(PC)への転送」の2役をこなす必要がある。公式サンプルがRX→PC転送をWiFi UDPでなくUSBシリアルにしているのは、RXノードのWiFiインターフェースを「CSI受信（AP接続 or promiscuousモードでの傍受）」専念させ、PCへの転送という別の通信を同居させない設計判断だった可能性がある——1つの無線チップで「CSI受信」と「UDP送信」を同時にこなすと、CSI受信のタイミング・パケットロスに干渉するリスクが未検証のまま残る。上記の「WiFi UDP継続案 vs USBシリアル案」比較実験は、この干渉が実際に起きるかどうかを確かめることが核心になる
- **推奨チップ**：公式のCSI性能ランキングは`ESP32-C5 > ESP32-C6 > ESP32-C3 ≈ ESP32-S3 > ESP32`。当時購入済みだったNanoC6(C6)は上位グループだったが、その後採用断念（上記「現在のハードウェア状況」参照）。実際に実機検証したATOM Lite（ESP32無印）はこのランキング最下位で、`#22`で見つかった制約と無関係ではなさそう
- **ESP32-C6の既知バグ**：`esp-csi` issue #233（Open、未マージ）——C6は5GHz非対応なのに`csi_recv`/`csi_send`が無条件に5GHz帯を有効化しようとして動かない。C6でビルドする際は該当`#ifdef`分岐からC6を除外するパッチが必要

1. **【解決済み・要clean up】SpecificDeviceCSIはArduino frameworkでは機能しない。素のESP-IDFなら動作確認済み**：`src/csi_tx.cpp`/`src/csi_rx.cpp`（Arduino版）ではAP非接続+promiscuousでCSIコールバックがほぼ発火しない問題があり（`#22`）、チップをAtomS3 Lite(S3)に変えても再現した（`#23`）。原因はチップではなく**Arduinoのesp_now実装に送信レート明示指定API`esp_now_set_peer_rate_config()`が存在しないこと**だった。独立プロジェクト`idf_csi_test/`（RX=AtomS3 Lite）・`idf_csi_test_tx/`（TX=元祖ESP32、いずれも`framework=espidf`）で、①`sdkconfig.defaults`に`CONFIG_ESP_WIFI_CSI_ENABLED=y`を追加②TX/RX双方に`esp_now_set_peer_rate_config()`（HT40/MCS0_LGI）を追加、の2点を直したところ`csi_matched`がTXの送信レート(100Hz)とほぼ1:1で取れるようになった（`#24`）。**次にやること**：①`src/csi_tx.cpp`/`src/csi_rx.cpp`（Arduino版、動作しない診断コード）の扱いを決める（削除 or Arduino非対応の注記を残して放置）②`idf_csi_test`/`idf_csi_test_tx`を清書し、TX1台+RX複数台のブロードキャスト型構成へ発展させるか判断③InterDeviceCSIも同様にArduinoで壁に当たるか検証（未確認）
2. **`diff_score`をサブキャリア0〜50帯（Legacy LTF）限定に改修する**：`main.cpp`の`diff_score`計算を該当帯域のみに限定するよう修正し、実機で動きの検知精度が改善するか確認する
3. **C3サブキャリア形状によるドリフト補正の再現性確認**：`#20e`/`#20f`は1セッション・11区間のみの結果。別セッションで往復データを録り直し、同じ傾向（形状ベース判定が外れ値ケースを補正できる）が出るか確認する
4. **経路遮蔽仮説の再現性確認**：`#14`・`#18`で支持する結果は得られたが、いずれも1回きりの試行。次回は遮蔽の開始/終了もアプリでタップし、複数回試行して再現性を確認する
5. **avg_ampの揺らぎ差の再現性確認**：「寝ている」「離れた」をもう1〜2回、揃った時間で撮り直し、標準偏差の差が再現するか確認する
6. **SpecificDeviceCSIへの本格移行判断**：上記1の元祖ESP32での制約発見を受けて、S3/C3での再検証結果を踏まえて判断する
6b. **【将来検討】5GHz帯でのCSI検証**：フレネルゾーンが約1.5倍狭くなり遮蔽検知に理論上有利。ESP32-C5が候補だが、5GHzモードでのCSI抽出が同様に使えるか未確認
