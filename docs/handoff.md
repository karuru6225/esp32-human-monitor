# 引き継ぎメモ（2026-08-30時点）

このプロジェクトのこれまでの経緯・検証結果・現状の判断をまとめたもの。
README.mdが「プロジェクト概要」だとすると、こちらは「途中経過の詳細と、次に何をすべきか」の記録。

## 経緯（なぜこの方向に進んでいるか）

1. Home Assistantで「いつ何をしていたか」の活動ログ（就寝中/作業中/休憩中/外出中、将来的にはもっと細かく）を可視化したい、というのが元々のゴール
2. 既存のモーションセンサーは玄関付近にしかなく、リビングでの在宅勤務中の在室・静止状態を検知できない、という制約が判明
3. mmWaveレーダー（Aqara FP2やSeeed XIAOシリーズ）を検討したが、技適（技術基準適合証明）の確認・取得の手間が課題として浮上
4. 代替として、既に技適済みのWiFi無線をそのまま使う「WiFi CSI（Channel State Information）センシング」を検証する方針にした。専用レーダーHWの購入・技適確認が不要なのが利点
5. 実装方式はESPHome + `espectre`外部コンポーネントも検討したが、コードレベルの細かい制御がしたいという要望から、**PlatformIO + Arduino framework**での自作ファームウェアを本命ルートとして選択
6. **重要な制約**：この検証段階ではMQTT/Home Assistant連携は行わない。まずはシリアルモニタで生の数値を見て、そもそもCSIが人の動き・在室状態に反応するかどうかだけを確認する

## ファームウェアの現状（`src/main.cpp`）

PlatformIO + Arduino framework、`esp_wifi_set_csi_rx_cb`でCSIコールバックを受ける。当初はシリアル出力のみの単体検証用コードだったが、2026-08-30にサブキャリア別振幅をWiFi UDPでPCへ送信する機能を追加した（下記）。シリアル出力は現在も以下の4つの指標を出す：

- `rssi`：受信パケットの信号強度（`info->rx_ctrl.rssi`）。近い/遠いの粗い判定に一番安定して使える
- `avg_amp`：CSIバッファの生バイトを空間方向（サブキャリア間）に絶対値平均したもの。I/Qが交互に並んだ生データをそのまま平均している粗い指標で、動きへの感度は低め
- `diff_score`：前フレームとの差分の絶対値平均（時間方向の変化＝動きの指標として追加）。**注意**：当初は「歩く・体を動かすといった能動的な動作にスパイクとして反応する」という触れ込みだったが（#3の単体検証ではその通りだった）、#11〜#14の複数ノード検証では終始ノイズに埋もれてほとんど機能しなかった。原因は192本全帯域を平均していたことで、Legacy LTF帯（サブキャリア0〜50）だけに絞れば動きに鋭く反応することが#17で判明している（現状のコードはまだ未修正、次のアクション候補1参照）
- `filt=採用数/受信総数`：CSIコールバックの送信元MACが接続中APのBSSIDと一致するものだけを採用するフィルタを追加した際の採用率（詳細は後述）

**解決済み**：WiFi認証情報は`src/secrets.h`（`.gitignore`済み）に分離した。`main.cpp`は`secrets.h`をincludeして`WIFI_SSID`/`WIFI_PASSWORD`マクロを参照する形。テンプレートとして`src/secrets.h.example`をコミット対象に置いてある。新しい環境でビルドする際は`secrets.h.example`を`secrets.h`にコピーして値を入れること。

**2026-08-30追加**：サブキャリアごとの振幅（`sqrt(I²+Q²)`、`info->buf`のQ/Iペアから正しく計算）をWiFi UDPでPCへ送信する機能を追加した。シリアル(115200bps)だとサブキャリア192本ぶんのデータを流すには帯域が足りないため、WiFi UDP（`PC_IP`/`PC_PORT`宛、`CsiUdpHeader`構造体）に転送する方式にした。送信先IPは環境ごとに`main.cpp`内の`PC_IP`を書き換える必要がある。ヘッダには自機のMACアドレス（`own_mac`）を含めている——後述のDocker越し受信だと送信元IPがNATで潰れて複数台を区別できないため。

## ツール構成（`tools/`）

- **`tools/csi_listener/`**：PC側でCSIデータ・位置報告を受信するリスナー。Docker化済み（`docker build -t csi-listener .` → `docker run -p 5005:5005/udp -p 5006:5006/udp -v ./data:/data csi-listener`）。UDP:5005でサブキャリア振幅データ（`CsiUdpHeader`形式）、UDP:5006でスマホからの位置報告（JSON）を受け、それぞれCSVに書き出す。**Windows Git BashでDocker実行する際は`MSYS_NO_PATHCONV=1`を付けないと`-e`の値のパスが勝手にWindowsパスへ変換されて壊れるので注意**
- **`tools/position_reporter/`**：Flutterで作ったAndroidアプリ。「椅子」「ベッド」「玄関」「不在」ボタンをタップすると、その場でPC(`tools/csi_listener`)へUDP(JSON)で位置ラベル+時刻を送る。チャットで移動時刻を逐一報告する代わりに使う。ビルド・実機インストールは`flutter build apk --release` → `adb install -r build/app/outputs/flutter-apk/app-release.apk`（`flutter run`は実機にアタッチしたまま常駐するプロセスなので、ワンショット実行には使わないこと）。`AndroidManifest.xml`に`INTERNET`権限が必要（デフォルトでは入っていないので注意）

### 得られた知見

- **粗い位置変化（歩いて近づく/離れる）**：RSSIの平均値シフトだけで十分検出できる。#1, #2で再現性を確認済み
- **能動的な動作（座って作業中の体動）**：`diff_score`の散発的なスパイクとして拾える。#3では離れた状態の3σを超えるスパイクが624サンプル中18回（2.9%）発生していたが、#4（寝ている）・#5（離れた）では0回
- **静止していても在室/不在を区別できるか（当初の本命課題）**：#3〜#5で「座っている > 寝ている > 離れた」という綺麗な段階的パターンがrssi/avg_amp両方の標準偏差に現れた。特にavg_ampの標準偏差は寝ている(1.25)が離れた(0.65)の約2倍あり、じっとしていても在室/不在の違いが信号の"揺らぎの大きさ"に出ている可能性がある。**当初のPIRセンサーでは検知できない「静止した在室状態」を拾えるかもしれない、という意味で初期段階で一番の収穫だった一節**（その後#13〜#18でサブキャリア分解・経路遮蔽仮説・フレネルゾーン理論による配置最適化・移動方向推定と、より具体的で実用度の高い知見が積み上がっているので、現時点では数ある収穫の1つという位置づけ）
- **MACフィルタの実験結果（#7）**：CSIコールバックの送信元MACをAPのBSSIDに絞るフィルタを追加したが、採用率は常に100%だった。つまり「同一チャンネル上の他端末の通信を誤って拾っていた」という仮説は誤りで、STAモードのWiFiドライバは元々AP由来のフレームしかCSIコールバックに渡していなかったと考えられる。これにより、残っているノイズ（ルーターの自動レート制御・再送・ビームフォーミングなど）はAP側の挙動に起因するもので、**ESP32側だけでは制御できない**ことが裏付けられた
- **チップ差 vs アンテナ実装差（#8〜#10、2026-08-30）**：car-iot機（自作PCBアンテナ）とXIAO C3（市販・外付けアンテナ）を同一地点に並べても約12dBのrssi差が出た（#9）。しかしcar-iot機の代わりに市販品のM5AtomS3 Lite（同じくESP32-S3だが外付けアンテナ）で比較し直すと差はわずか2.3dBまで縮小し、diff_scoreの平均・3σ誤検知率もほぼ同水準になった（#10）。**ESP32-S3とESP32-C3自体のCSIセンシング特性に大きな差はなく、car-iot機の信号品質の悪さはアンテナ実装（自作PCBトレース）に起因する**と判断できる
- **近いノードと遠いノードで移動イベントへの反応パターンが質的に違う（#11、2026-08-30）**：クリーンな機体（AtomS3・XIAO C3）で椅子からの離席→復帰を2回行ったところ、**遠いノード（C3、ベッド頭付近）は離席中ずっとrssiが7〜8dB下がる持続的なレベルシフト**を示し、**近いノード（AtomS3、椅子付近）は復帰の瞬間だけ数秒間rssiが落ちる一過性の反応**を示した。2サイクルとも同じパターンが再現している。`diff_score`は終始高いノイズの帯になっていて、この程度の歩行イベントを判別する材料としては機能していない（グラフで一目瞭然）

  ![離席復帰時のrssi/diff_score波形（AtomS3 vs XIAO C3）](images/zone_test_260830_leave_return.png)

- **「離れた場所への移動」と「近づく移動」で反応の質がさらに違う（#12、2026-08-30）**：#11は椅子からベッドと無関係な玄関方向への移動だったが、#12では逆に**人がC3(ベッド)自体に近づく**移動を試した。結果、C3のrssiは#11のような一定した下げ幅ではなく、**近接時ほど大きく・かつ試行ごとにばらつく**下降（1回目-48〜-53、2回目-58〜-62）を見せた。人体がアンテナのごく近くにあることによる**近接場の遮蔽効果**が、単純な在室/不在の差より支配的になっていると考えられる。また`diff_score`も#11では終始ノイズに埋もれていたが、#12ではAtomS3側にt=130〜155付近で明確なスパイクの帯が出た。**`diff_score`はノードの近くでの動きにしか反応せず、`rssi`は近接時の体遮蔽と遠隔時の在室/不在とで異なる質の変化を示す**、という構造が見えてきた

  ![椅子↔ベッド移動時のrssi/diff_score波形（AtomS3 vs XIAO C3）](images/zone_test_260830_tobed.png)

- **サブキャリア別振幅なら位置ごとに分離できる兆しがある（#13、2026-08-30）**：単一スカラー(rssi/avg_amp)ではなく、CSIバッファをサブキャリアごとに`sqrt(I²+Q²)`で正しく振幅計算し（WiFi UDPでPCへ送信、詳細は上記「ツール構成」）、約30分の自由行動データを位置ラベル（椅子/ベッド/玄関）ごとに平均・比較した。結果、**AtomS3は「玄関」を椅子・ベッドの両方から明確に分離（機体内ばらつきの1.3〜1.6倍）**、**C3は「椅子」を分離（0.9倍）**できたが、AtomS3の椅子vsベッド、C3のベッドvs玄関はそれぞれ分離が弱かった（0.56倍, 0.38倍）
  - 間取り図で位置関係を確認したところ、**C3・椅子・ルーターの座標がほぼ一直線上に並ぶ配置**だと判明（C3→ルーター直線上での椅子位置の予測誤差はわずか7px程度）。これにより、**「ノード↔ルーター間の直接伝搬経路（フレネルゾーン）を人体が遮ったかどうか」が支配的要因**という仮説が立つ：C3にとって椅子は自分↔ルーター経路の真上にあるため人が座ると強く遮る一方、ベッド(近接場)と玄関(遠方)はどちらもその経路の"外"にあるため似た影響になり分離しにくい。AtomS3はルーター・げんかんの開口部の近くにいるため、玄関への行き来がAtomS3↔ルーター経路を横切りやすく、玄関が一番分離できる、という説明も筋が通る
  - **未検証の仮説**：今回は自由行動1回きりの間取りからの逆算であり、直接確認していない。同じ距離でも経路の内側/外側に意図的に立って比較すれば切り分けられる
  - 生データにはLTFセグメント継ぎ目のアーティファクト（規則的な0埋め区間・単発の異常スパイク）が乗るため、解析時は除外が必要（`docs/images/subcarrier_position_260830.png`は除外済み版）
  - **物理的な裏付け（フレネルゾーン）**：2.4GHzの波長は約12.5cm。障害物が電波を遮るかどうかは波長そのものより、送受信点間の距離にも依存する第1フレネルゾーン半径`F1=√(λ・d1・d2/(d1+d2))`（d1,d2は障害物から送受信点それぞれまでの距離）で決まる。今回の部屋スケール（ノード↔ルーター間5m程度、障害物が中間）だとF1≈40cm。人体（胴回り30〜40cm）はこの太さと同程度かそれ以上あり見通し線周辺の"通り道"を実質的に塞ぐサイズだが、布団は同じ2次元的な影の位置にあっても3次元的な体積の占有量・誘電損失（水分含有量）が小さく、遮蔽効果が弱い（#15の結果と整合）

- **経路遮蔽仮説（#13）の直接検証、結果は支持的（#14、2026-08-30）**：AtomS3を「ベッド↔ルーター直線上」に意図的に再配置して検証。**横になっている間(約3.5分)AtomS3のrssiが-53〜-54で終始安定して低く**、それまでの弱い分離（AtomS3のベッドvs椅子=0.56倍）とは対照的な"持続的に遮られている"状態が見えた。さらに、椅子復帰直前に**C3だけを狙って遮る位置**へ数十秒移動したところ、**C3のrssiは下降(-50→-52.55)、AtomS3は逆に上昇(-53.16→-48.58)**という、狙い通り逆方向の変化が同時に起きた。経路遮蔽仮説を支持する結果と言えそう

- **HAの玄関モーションセンサーとのクロスバリデーション（2026-08-30）**：Home Assistant連携はまだ本格導入していないが（MCP経由でGetLiveContextのみ利用可）、既存の「開閉センサー F2 モーション」（エリア「室内」、名前は紛らわしいが玄関付近を検知するセンサー）の履歴をユーザーがHA画面で確認したところ、**15:27・15:31に動体検出があり、#19のテストで玄関にいた時刻（15:27:54〜15:28:34、15:31:44〜15:31:50）とほぼ一致**した。椅子・ベッドの時刻では検出が出ておらず、このセンサーが玄関付近だけをカバーしているという当初の前提（プロジェクトの出発点）とも整合する。**アプリでの位置タップが実際の行動を正しく反映していたことの独立した裏付け**が取れた。ただし、HAの「アクティビティ」（ロジックブック）表示では同じセンサーの15:27・15:31のイベントが見当たらず11:56:24で途切れており、**HA内部でも履歴ビュー間でデータの欠損・不整合がある**ことが分かった。今後HAとの本格連携をする際は、このデータ欠損問題も考慮する必要がある

- **静止時でも`diff_score`の3σスパイクは偶発的に発生する（#9, #10）**：動きが全くない状態でも、車iot機で0.19%、M5AtomS3 Liteで0.07%、XIAO C3で0〜0.13%の割合で3σを超えるスパイクが発生した。将来`diff_score`を動き検知の閾値判定に使う場合、この誤検知ベースラインを踏まえた閾値設計が必要
- **1台のノードでも、その場所から離れた場所での人の動きに反応することがある（#8、要再現確認）**：椅子の近くから離れた場所（ベッド頭付近）に置いたXIAO C3が、椅子への「復帰」イベントの瞬間から+7〜8dB・30秒以上持続するrssi上昇を示した。物理的に近接していない場所での行動が、部屋全体のマルチパスを通じて別ノードのCSI/rssiに影響する可能性を示唆するが、1試行のみでノイズとの区別がついていない

- **ノードの設置意図で「ゾーン占有センサー」にも「通過検知センサー」にもなる（#20、2026-08-30）**：#14・#18ではノード↔ルーター直線上に「留まる場所（ベッド・椅子）」を置き、滞在中ずっと持続するrssiレベルシフトを得ていた。今回はAtomS3を「玄関へ向かう際に人体が通る場所（滞在せず通過するだけの地点）」に置いたところ、**静止状態でのrssiはゾーンによらずほぼ一定（-39.9〜-40.5dB、std0.5以下）になり、ゾーン判定の材料としては機能しなくなった**。しかし移動の瞬間だけはC3と同様にサブキャリア0〜50帯の乱れが鋭く反応しており（11/11のイベントで確認）、rssiレベルでの滞在判定ではなく「今まさに人がそこを通過した」というイベント検知として使える。**同じ物理原理（経路遮蔽）でも、ノードをどこに置くかで得られる情報の性質（滞在 vs 通過）が変わる**、という設置設計上の知見

- **トリップワイヤー配置は「静止位置の2値判定」には不利——ノード間差分によるドリフト打ち消し効果が失われる（#20b、2026-08-30）**：#20のデータに#19bと同じ「椅子 vs それ以外」分類器（rssi差分の最近傍判定）をそのまま適用したところ、**精度が92.7%(#19b)から80.5%に悪化**した。誤分類はテスト中盤の椅子区間1つと終盤の玄関区間1つがまるごと逆判定される形で集中していた。特徴量`rssi(C3)-rssi(AtomS3)`が実質C3単体の値で決まるようになったことが背景だが、**1秒刻みで内訳を見ると2区間の原因は別物だった**（追加検証）：中盤の椅子区間は最初9秒がdiff=-4〜-9で完全に正しく判定され、残り9秒（ちょうどベッドタップ直前）だけ0付近に浮いて誤判定——これは移動を始めてからアプリのタップが遅れた**ラベル遅延**で、#19bで確認済みの「センサーがタップより先に反応する」現象と同種であり、センサーの誤りではない。一方、終盤の玄関区間は最初と最後の1秒だけ正しく、**真ん中12/14秒がまるごと椅子域(-5〜-7)に沈み込む持続的な外れ値**で、こちらは境界のズレでは説明できず、C3のセッション内ドリフト/外れ値という当初の解釈が妥当。#17で「ノード間差分は共通ドリフトを打ち消す」と確認していたが、**それは両ノードがそれぞれゾーン依存の変化を持つ場合にのみ機能する前提条件付きの効果**だったと分かった。**同じ経路遮蔽の原理でも、設置目的（滞在検知 vs 通過検知）によって2値分類器としての向き不向きが逆転する**——通過検知に向く配置は、静止位置の判定精度をむしろ下げるトレードオフがある

- **トリップワイヤーの乱れピークの大きさで、移動が玄関がらみかベッドがらみかを完全に判別できた（#20c、2026-08-30）**：ユーザーの仮説（「rssiの差が大きく変動したときに、一定以上SCの乱れがあるかどうかで玄関方向への移動かがわかりそう」）を検証。10回の移動イベントそれぞれでAtomS3のサブキャリア0〜50帯乱れのピーク値（タップ前後±3秒）を求めたところ、**玄関がらみの遷移（6件、乱れ3.10〜5.79・平均4.06）とベッドがらみの遷移（4件、乱れ1.61〜2.10・平均1.96）が完全に分離**し、中間の閾値1本（3.01）で**10/10正解**した。一方、仮説後半にあった「rssi差分の変化幅が大きいときに限定する」という条件は不要と判明——変化幅の大小（-5.4〜+6.4dBとまちまち）は玄関/ベッドどちらの群にも表れており、判別に寄与していたのは乱れピークの大きさだけだった。AtomS3が玄関への経路上のトリップワイヤーとして機能しているため、その経路を横切る移動だけを強く拾い、経路を通らない移動は弱くしか反応しない、という設置の物理と整合する。**「椅子かどうか」はrssi差分（#20bで80.5%）、「玄関方向かベッド方向か」は移動時のAtomS3乱れピークの大きさ、という2段構えの分類ロジックが有望**

- **2段構えのハイブリッド分類器を時系列全体に適用すると82.1%——ボトルネックは方向推定ではなくrssi差分側の1段目（#20d、2026-08-30）**：#20cの閾値をもとに「rssi差分で椅子/それ以外を判定→それ以外に切り替わった瞬間のAtomS3乱れピークで玄関/ベッドを決定」というロジックをテスト区間全体（190ビン）に実際に走らせたところ、**時間重み付き精度82.1%**（椅子recall81.5%、ベッドrecall100%、玄関recall61.3%）を達成した。#19の同種のハイブリッド方式（51.8%）から30ポイント以上の改善。誤分類の中身を見ると新しい失敗パターンは増えておらず、**#20bで切り分けた2区間（ラベル遅延1件・C3の外れ値1件）にそのまま起因**していることが確認できた——2段目（方向判定）は1段目が正しく機能した場面では一度も外していない。**この配置でさらに精度を上げるには、方向推定のロジックを改良するよりも1段目のrssi差分判定を安定させる方が効く**、という優先順位がはっきりした。ただしラベル遅延によるものはセンサー側の問題ではなく実運用上は許容できる誤差であり、実質的な改善余地はC3側の外れ値/ドリフト対策に絞られる
